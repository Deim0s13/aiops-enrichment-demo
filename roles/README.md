# Build roles

Roles used by the build phases in `playbooks/`.

| Role | Used by | Purpose |
|---|---|---|
| `vault_bootstrap` | `00_secrets.yml` | Runs Vault on the operator's laptop and configures its KV engine, policies and AppRoles |
| `secrets` | Every phase that needs a secret | The only place that reads secrets: resolves the names in `demo_required_secrets` from Vault or the local file, depending on `demo_secrets_backend`. Refuses to run at `-vvv` and above. When it reads the cluster group, it checks that the API is reachable and accepts the token before the phase changes anything |
| `olm_operator` | Phases that need an operator | Installs one operator through OLM (namespace, OperatorGroup, Subscription, then waits for the CSV), or adopts it if it is already installed. Checks the channel exists in the catalogue first, and enforces a minimum version. Records what it found in `olm_operator_results` |
| `postgres` | `02_openshift_ai.yml` (and phase 05) | The shared PostgreSQL: TLS from the service CA, generated passwords kept in the cluster, and a database and user per entry in `postgres_databases`, created by an idempotent Job. Publishes `postgres_connection` (host, port and credentials Secret) for its clients |
| `openshift_ai` | `02_openshift_ai.yml` | The platform team's part: checks OpenShift AI, installs Red Hat Connectivity Link, creates the Kuadrant instance and the MaaS gateway, switches on Models-as-a-Service and MLflow, and runs the MLflow server |
| `model_serving` | `02_openshift_ai.yml`, `evaluation/model_selection.yml` | The model owner's part: serves one model on vLLM as an `LLMInferenceService` behind the MaaS gateway and registers it with MaaS, or removes it and waits until the GPU is free (`model_serving_state: absent`). With `model_serving_exclusive`, it removes any other model first, for a GPU that holds one model |
| `maas_consumer` | `02_openshift_ai.yml`, `evaluation/model_selection.yml` | The application team's part: onboards one consumer to one model, with its own service account, a policy, a token budget and an API key that belongs to it, stored with the model's ID and URL in one Secret. Then checks access through the gateway |
| `aap` | `03_aap.yml` | The automation platform team's part: installs the AAP operator into its own namespace, runs the platform with the components in `aap_components` (automation controller and Event-Driven Ansible), checks it by logging in through the gateway, and attaches the subscription manifest from Vault |
| `servicenow` | `04_servicenow.yml` | The ITSM team's part: custom incident fields and choices, the on-call assignment group with a fictional engineer, the configuration items in the service map, a custom role per service identity and the identities themselves (with `itil`), generated passwords kept in the cluster and reset only when missing or no longer working, guard business rules that narrow `itil`, and the enrichment ready notification. Every record is found first, created if missing and changed only where it differs. Ends by acting as each identity to prove the guards hold. Its second entry point, `trigger` (phase 07), keeps the REST Message with the event stream's address and token and the business rule that posts qualifying incidents, and proves it with incidents raised as `svc-monitoring` |
| `ee_publish` | `07_execution_environment.yml`, on the laptop | Publishes the execution environment built on the laptop to the cluster's internal registry: gives the registry a route if needed, pushes only when the local image has changed, using a private auth file rather than putting the token on a command line, and reports the in-cluster address pinned by digest for AAP |
| `aap_content` | `07_aap_content.yml` | The automation team's part: declares the demo's AAP content as data and applies it with `infra.aap_configuration` (organisation, project, execution environment, ServiceNow credential type and credential, inventory, the three enrichment job templates, the workflow with its failure branch, the trigger's AAP user, and in EDA a project, decision environment, event stream and rulebook activation), the four diagnostic job templates, run as the `aiops-diagnostics` service account it creates through a time-limited token it renews, and the monitoring integration stand-in (its job template, ServiceNow credential, AAP user, Basic-authenticated event stream and activation). Generated secrets are kept in the cluster and reused. Ends by proving the trigger, the failure branch, idempotency and the trigger user's limits on test incidents. Its second entry point, `checks_integration`, runs after the ServiceNow trigger exists and proves the integration from alert to enriched incident |
| `enrichment_service` | `06_enrichment.yml` | The application team's part: builds the enrichment service in the cluster from `services/enrichment` only when it has changed, deploys it pinned by digest behind TLS from the service CA with its own API token and MaaS key, applies default-deny and allow-from-AAP network policies, and checks it from inside the cluster with Jobs in the allowed and a refused namespace |
| `verify` | `verify.yml` | The M2 acceptance checks: time to note, no retrigger, a safe retry, an engineer's concurrent edit, and the unavailable path with the enrichment service stopped and always restarted. Keeps its incidents for review unless `verify_cleanup` is true |
| `demo_reset` | `reset.yml`, `08_workload.yml` | Resolves and closes the demo's own incidents with a close note, and deletes build-check leftovers. Touches nothing else in the PDI. Phase 08's check uses it, limited to one problem's correlation ID, to start from a fresh incident |
| `incluster_build` | `06_enrichment.yml`, `08_workload.yml` | Builds an image in the cluster with OpenShift Builds from a directory of this repository, with the read-only GitHub token, only when that directory has changed; returns the image pinned by digest |
| `workload` | `08_workload.yml` | The application team's sample service: builds and deploys `payments-notify` with its heap metrics, alert rules, alert routing to the integration stand-in, network policies and the diagnostics' view of its namespace, and proves the single fault scenario end to end, from the OOM kill to the enriched incident. Its second entry point, `restart` (`reset.yml`), restarts the service with a new pod, clearing a recurring fault |
| `platform` | `01_platform.yml` | Frees the GPU, checks the GPU stack and default storage the environment provides, and enables user workload monitoring with its Alertmanager. Installs no operators (DD13) |

## Conventions

- **Inputs, not kit settings.** Each role takes role-prefixed inputs, and the playbook fills them from the kit's `demo_*` settings in `inventory/group_vars/all/main.yml`. The roles do not read `demo_*` themselves, so each can be called on its own, for example `model_serving` once per candidate model in the model test. The `secrets` and `vault_bootstrap` roles are the exception: they exist to serve the kit's settings.
- **Required inputs are declared** in each role's `meta/argument_specs.yml`, so a missing or misspelt input stops the play before the role changes anything.
- **Roles find what they need on the cluster.** `maas_consumer` reads the MaaS address from the gateway rather than from `openshift_ai`, as an application team would.
- **Cluster access** comes from the `module_defaults` the calling play sets.
