Rate limits

Every API client has a request limit, so that one customer's traffic cannot affect another's.

How limits work

Limits apply per client ID, as requests a minute, over a sliding 60-second window. Every instance that sends with the same client ID shares the same limit. The Standard plan allows 3,000 requests a minute for each client, and the Business plan 10,000. A client may burst to twice its limit for up to 10 seconds.

When a client reaches its limit

Requests over the limit are refused with HTTP 429 Too Many Requests and are not queued by MessageHub. The response carries a Retry-After header, the seconds to wait before the client's next request will be accepted, and X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset headers. A request sent before Retry-After has passed is refused again and counts against the limit.

Checking a client's usage and limit

In the MessageHub Console, open Clients, select the client ID and open Usage: it shows requests a minute against the limit for the last 7 days, and any 429 responses. The same figures are returned by GET /v2/clients/{client_id}/usage with an organisation administrator's API key. Compare the request rate in Usage with the rate your service believes it sends: if Usage shows more requests than you send, retries are being counted.

Common causes of unexpected throttling

  • Retries sent before Retry-After has passed, so each refused request is followed by more.
  • More instances of a service sharing one client ID, after scaling out.
  • Scheduled bulk sends, such as month-end statements, through the same client as real-time messages.
  • A lower limit after a plan change, or limits reduced during a MessageHub incident (degraded mode, see Status and incidents).
