# Security and secrets

This repository is written to be safe to share publicly. It never contains a secret in any form, including secrets encrypted with Ansible Vault, because an encrypted file in a shared repository still means a shared password. Each person who runs the kit brings their own credentials, and everything the kit can generate for itself, it generates.

## Where secrets come from

| Category | Examples | Source | Lifetime |
|---|---|---|---|
| Personal entitlements | OpenShift pull secret, AAP subscription manifest, Automation Hub token, registry.redhat.io credentials | Your own Red Hat account, stored in your own Vault | Yours; never shared |
| Environment access | Cluster API URL and token | Issued with each demo environment, stored in your Vault | One environment |
| ServiceNow administration | PDI URL and administrator credential, used only to create the demo's service identities | Your own PDI, stored in your Vault | Yours |
| Generated | AAP administrator, database passwords, model gateway key, EDA token, ServiceNow service identity passwords | Generated by the playbooks at build time | One build; held only as Kubernetes Secrets in the cluster |

Generated secrets never leave the cluster and disappear with the environment, so there is nothing to rotate or hand over.

## HashiCorp Vault on your laptop

The recommended backend is HashiCorp Vault Community Edition, run as a container on your laptop by `playbooks/00_secrets.yml`. It is free to use for this purpose under the Business Source License. OpenBao works the same way if your organisation's policy requires an OSI-approved licence.

- Vault runs with file storage on a persistent Podman volume, not in dev mode.
- Keep the unseal key and root token in your password manager. Use the root token only to set Vault up.
- The playbooks authenticate with an AppRole bound to a read-only policy on the demo's KV path. Supply the role ID and secret ID through the `VAULT_ROLE_ID` and `VAULT_SECRET_ID` environment variables.
- Enter secret values yourself through the Vault CLI or UI, so they never pass through a file.
- The demo cluster cannot reach your laptop, so Vault is used only during the build. The running demo never depends on it.

Secrets are read from a KV version 2 engine mounted at `aiops-demo`:

| Path | Keys |
|---|---|
| `aiops-demo/entitlements` | `pull_secret`, `aap_manifest_b64`, `automation_hub_token`, `registry_username`, `registry_password` |
| `aiops-demo/cluster` | `api_url`, `api_token` |
| `aiops-demo/servicenow` | `instance_url`, `admin_username`, `admin_password` |

## Without Vault

Set `secrets_backend: local` and copy `secrets.example.yml` to `~/.config/aiops-demo/secrets.yml`, outside the repository. Encrypt it with your own `ansible-vault` password. The keys mirror the Vault paths above.

## Guardrails

- **Pre-commit hooks** run gitleaks, yamllint and ansible-lint before every commit. Run `pre-commit install` once after cloning.
- **CI** runs the same checks on every push and pull request.
- **GitHub secret scanning and push protection** are enabled once the repository is public.
- **`no_log: true`** is set on every task that handles a secret, so values stay out of console output and AAP job logs.
- **ansible-navigator playbook artefacts are disabled** in the committed configuration, because they record every variable, including secrets.
- **The execution environment and container images contain no secrets.** Credentials are supplied at run time.
- **`.gitignore`** excludes the common secret file names, but it is a safety net, not a control.

## Content rules

- Use the fictional organisation and services only. No customer names, data, runbooks or screenshots.
- Keep your PDI instance name and cluster URLs in your own configuration, not in the repository, issues or pull requests.
- Diagnostic output is sanitised before it reaches the model or a work note. Treat log lines and ticket text as untrusted input.
- Check screen recordings and screenshots for tokens, URLs and instance names before sharing them.

## If a secret is committed

1. Revoke or rotate the secret first. Once pushed, assume it is compromised, even if the repository is private.
2. Remove it from history, for example with `git filter-repo`, and force-push.
3. Tell the repository owner, so forks and clones can be dealt with.

## Reporting a security issue

Please report security issues privately to the repository owner rather than opening a public issue.
