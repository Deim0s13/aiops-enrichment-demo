# Security and secrets

This repository is written to be safe to share publicly. It never contains a secret in any form, including secrets encrypted with Ansible Vault, because an encrypted file in a shared repository still means a shared password. Each person who runs the kit brings their own credentials, and everything the kit can generate for itself, it generates.

## Where secrets come from

| Category | Examples | Source | Lifetime |
|---|---|---|---|
| Personal entitlements | OpenShift pull secret, AAP subscription manifest, Automation Hub token, registry.redhat.io credentials | Your own Red Hat account, stored in your own Vault | Yours; never shared |
| Environment access | Cluster API URL and token | Issued with each demo environment, stored in your Vault | One environment |
| ServiceNow administration | PDI URL and administrator credential, used only to configure the PDI | Your own PDI, stored in your Vault | Yours |
| Source access | A fine-grained GitHub token, this repository only, contents read-only, for AAP's project and the in-cluster build | Your own GitHub account, stored in your Vault | Until it expires |
| Generated | AAP administrator, database passwords (including the knowledge index's ingestion and read-only identities), model gateway key, ServiceNow service identity passwords, the EDA users' passwords, the event stream token and the Alertmanager event stream password, the diagnostics' time-limited service account token, the enrichment service's API token | Generated by the playbooks at build time | One build; held as Kubernetes Secrets in the cluster. The diagnostics token also expires on its own after 7 days |

Generated secrets are held in the cluster and disappear with the environment, so there is nothing to rotate or hand over. Two also live where they are used: ServiceNow holds the event stream token in its REST Message, and the service identities' passwords are set on their ServiceNow accounts. Each new environment replaces both.

## HashiCorp Vault on your laptop

The recommended backend is HashiCorp Vault Community Edition, run as a container on your laptop by `playbooks/00_secrets.yml`. It is free to use for this purpose under the Business Source License. OpenBao works the same way if your organisation's policy requires an OSI-approved licence.

- Vault runs with file storage on a persistent Podman volume, not in dev mode. Its API is published on `127.0.0.1:8200` only. TLS is disabled on that listener because traffic never leaves the laptop.
- The first run writes the unseal key and root token to `~/.config/aiops-demo/vault-init.json` (mode 0600). Move both into your password manager and delete the file. Use the root token only to set Vault up and load secrets.
- The build reads each secret group (`entitlements`, `cluster`, `servicenow`, `source`) with its own AppRole, bound to a policy that can read that group and nothing else. A phase that needs only ServiceNow credentials therefore cannot read the pull secret, even by mistake. Tokens last one hour and carry no default policy. The credentials for all four AppRoles are written to `~/.config/aiops-demo/approle.env` (mode 0600) and supplied to the build through the `AIOPS_VAULT_APPROLES` environment variable. Secret IDs expire after 7 days and are rotated with each new demo environment; rotating revokes all earlier secret IDs, so only one per group is valid at a time.
- The build revokes each Vault token as soon as it has read that group.
- Enter secret values through the Vault CLI from standard input, as shown in [docs/laptop-setup.md](docs/laptop-setup.md), so they never appear on a command line, in shell history or in a file.
- The demo cluster cannot reach your laptop, so Vault is used only during the build. The running demo never depends on it.

Secrets are read from a KV version 2 engine mounted at `aiops-demo`:

| Path | Keys |
|---|---|
| `aiops-demo/entitlements` | `pull_secret`, `aap_manifest_b64`, `automation_hub_token`, `registry_username`, `registry_password` |
| `aiops-demo/cluster` | `api_url`, `api_token`, and optionally `api_ca_cert` (the cluster's CA bundle, which is not a secret but changes with each environment) |
| `aiops-demo/servicenow` | `instance_url`, `admin_username`, `admin_password` |
| `aiops-demo/source` | `github_token`: a fine-grained GitHub token, limited to this repository with Contents read-only, which AAP uses to sync the repository as its project (phase 07). Preflight checks that it can read the repository, and that a harmless test write is refused. Optional, for the knowledge loop (DD33, DD34): `github_app_id` and `github_app_private_key`, the knowledge bot's GitHub App, which can open pull requests but is not on `main`'s bypass list, so it cannot publish; and `github_reset_token`, your own fine-grained token with Contents read and write on this repository only, used only by `reset.yml -e demo_reset_knowledge=true` to remove the loop's resolutions from `main` |

## Without Vault

Set `demo_secrets_backend: local` and copy `secrets.example.yml` to `~/.config/aiops-demo/local/secrets.yml`, outside the repository. Encrypt it with your own `ansible-vault` password. The keys mirror the Vault paths above. See [docs/laptop-setup.md](docs/laptop-setup.md) for how to mount it into the execution environment.

## Guardrails

- **Pre-commit hooks** run gitleaks, yamllint and ansible-lint before every commit. Run `pre-commit install` once after cloning.
- **A local pre-commit hook blocks any `debug` task that references `secrets_values`**, the fact that holds every resolved secret. A troubleshooting `debug` is the easiest way to leak everything at once.
- **CI** runs the same checks on every push and pull request.
- **GitHub secret scanning and push protection** are enabled on the repository.
- **`no_log: true`** is set on every task that handles a secret, so values stay out of console output and AAP job logs. Where `no_log` would also hide a useful error, the playbooks run a separate check that involves no secret, so the error can be shown safely. Secret handling is tested at maximum verbosity (`-vvv`), with throwaway values, to confirm no value appears in the output.
- **No secrets at `-vvv` and above.** Ansible prints each module's arguments at that verbosity, and `kubernetes.core` prints the cluster token among them, even when the task succeeds. The cluster phases pass the token to every Kubernetes task through `module_defaults`, so hiding each task with `no_log` would also hide every error. Instead, the `secrets` role refuses to resolve secrets at verbosity 3 or higher. Debug with `-vv`. `secrets_allow_debug_verbosity=true` overrides this, for throwaway credentials only. At `-vv`, a task that loops over a Kubernetes task's registered results would print the token too, so the playbooks never do that.
- **The enrichment service's MaaS API key** is minted by the build with a 10-minute token for the service's own service account, stored only in the `maas-api-key` Secret in `aiops-enrichment`, and never printed: the access checks report status codes only. A rebuild tests the stored key and mints a new one only if it no longer works.
- **The enrichment service's MLflow token** is not stored anywhere: OpenShift mounts a one-hour token for the service's service account into its pod and renews it, and the account may only create and read MLflow experiments and traces in its own namespace. Traces hold sanitised evidence and prompts only, and the MLflow client's telemetry is switched off, so nothing is reported outside the cluster.
- **ansible-navigator playbook artefacts are disabled** in the committed configuration, because they record every variable, including secrets.
- **The execution environment and container images contain no secrets.** Credentials are supplied at run time.
- **The cluster API certificate is always verified**, against the cluster's own CA bundle when one is loaded, so the cluster token is only sent to the real cluster. Turning verification off (`demo_cluster_validate_certs=false`) is a last resort.
- **`.gitignore`** excludes the common secret file names, but it is a safety net, not a control.

## Content rules

- Use the fictional organisation (ACME Bank) and its services only. No customer names, data, runbooks or screenshots.
- Keep your PDI instance name and cluster URLs in your own configuration, not in the repository, issues or pull requests.
- Diagnostic output is sanitised before it reaches the model, a trace or a work note. Treat log lines and ticket text as untrusted input.
- Check screen recordings and screenshots for tokens, URLs and instance names before sharing them.

## If a secret is committed

1. Revoke or rotate the secret first. Once pushed, assume it is compromised, even if the repository is private.
2. Remove it from history, for example with `git filter-repo`, and force-push.
3. Tell the repository owner, so forks and clones can be dealt with.

## Reporting a security issue

Please report security issues privately to the repository owner rather than opening a public issue.
